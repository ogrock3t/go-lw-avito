# Trip Service

HTTP-сервис на Go для управления поездками. Сервис создает поездки, возвращает их по `id` и завершает поездки, принимает координаты и отдает маршрут. Фоновый сканер запрашивает координаты устаревших активных поездок через Push Service. Данные хранятся в PostgreSQL.

## Архитектура

Код разделён на слои и пакеты по действиям:

| Пакет | Назначение |
|---|---|
| `cmd/trip-service` | Чтение конфигурации, запуск сервера и обработка сигналов остановки |
| `internal/config` | Загрузка и валидация переменных окружения |
| `internal/container` | Создание конкретных реализаций и связывание зависимостей |
| `internal/domain/trip` | Сущности, статусы, доменные ошибки и переход состояния через `Trip.Finish` |
| `internal/model` | Структуры передачи данных между слоями |
| `internal/usecase/trip/{create,get,finish,savepositions,getpositions}` | Сценарии работы с поездками и координатами |
| `internal/http` | HTTP-обработчики, валидация, преобразование ответов и middleware |
| `internal/http/domainerror` | Единый маппинг доменных ошибок в HTTP Problem |
| `internal/repository/trip` | SQL-запросы и преобразование данных PostgreSQL |
| `internal/worker/positions` | Сканер, ограниченная приоритетная очередь, пул воркеров и метрики опроса |
| `internal/gateway/push` | HTTP-клиент Push Service |
| `internal/infra` | Пул PostgreSQL, менеджер транзакций и OpenTelemetry |
| `internal/generated` | Типы и серверные интерфейсы, сгенерированные из OpenAPI |

HTTP-обработчики вызывают usecase через интерфейсы. Usecase использует доменные
модели и узкие интерфейсы репозитория, менеджера транзакций и бизнес-метрик.
Конкретные реализации находятся в repository, infra, worker и gateway. Домен не зависит от
HTTP, PostgreSQL и OpenTelemetry; usecase не зависит от транспорта и драйвера БД.

Интерфейсы объявлены в `contract.go` пакета-потребителя. Каждый обработчик и
usecase определяет только нужные ему методы, поэтому зависимости остаются
узкими, а реализации можно подменять в тестах. Моки генерируются через
`go:generate` в `mocks_test.go` рядом с тестируемым кодом.

Все зависимости собираются вручную в `internal/container`. Main читает
конфигурацию, вызывает `container.New` и `Start`, запускает сервер и обрабатывает
остановку приложения. `Start` запускает сканер и воркеров.

## Требования

- Go 1.26
- `tripgoctl`
- PostgreSQL

## Быстрый запуск

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

`tripgoctl environment start` создает локальный `.env`. Файл `.env` не
коммитится. Пример переменных лежит в `.env.example`. Окружение лабораторной
работы 3 включает PostgreSQL, observability и Push Service. `tripgoctl connect`
показывает адреса сервисов и данные входа в Grafana.

```bash
make migrate
make run
```

## Makefile

```bash
make generate        # сгенерировать OpenAPI-код
make migrate         # алиас на migrate-up
make migrate-up      # применить миграции
make migrate-down    # откатить последнюю миграцию
make migrate-status  # показать статус миграций
make run             # запустить сервис
make test            # unit-тесты с race detector и итоговым покрытием
make test-integration # интеграционные тесты репозитория и telemetry пула с PostgreSQL
make lint            # проверить код линтером
```

`make test` сохраняет профиль покрытия в `coverage.out` и в конце печатает
суммарное покрытие. Пакеты `internal/domain/...` и `internal/usecase/...`
покрываются этим же запуском.

## Тестирование

Unit-тесты запускаются без PostgreSQL. Тесты HTTP-гейтвея и остановки приложения
поднимают локальные HTTP-серверы.

```bash
make test
```

Команда запускает тесты с `-race`, сохраняет профиль в `coverage.out` и печатает
общее покрытие. Репозитории и менеджер транзакций в unit-тестах usecase
подменяются через gomock. В тестах сканера используется управляемый тикер,
синхронизация выполняется через каналы. `goleak.VerifyTestMain` в пакетах
`internal/worker/positions` и `internal/container` проверяет отсутствие утечек
горутин.

Тесты фонового компонента покрывают дедупликацию, отмену, переполнение,
приоритет и вытеснение задач, ограничение числа одновременных отправок,
продолжение работы после ошибок, доработку очереди и отмену по таймауту
остановки. Тесты контейнера проверяют порядок остановки HTTP-сервера, сканера,
воркеров и закрытия ресурсов.

Требование покрытия domain/usecase не ниже 50% отдельно по пакетам проверяется
следующей командой.

```bash
go test -race -cover ./internal/domain/... ./internal/usecase/...
```

Integration-тесты используют реальный PostgreSQL из окружения курса. Перед
запуском нужно поднять окружение и применить миграции:

```bash
tripgoctl cluster start
tripgoctl environment start
make migrate
make test-integration
```

`make test-integration` загружает `DATABASE_URL` из `.env` и запускает тесты
репозитория и инструментированного пула с тегом `integration`, флагами `-race`
и `-count=2`. Тесты проверяют операции с поездками, откат транзакции при ошибке
вставки истории, сохранение запоздалых координат, откат сохранения координаты,
выборку устаревших поездок и DB telemetry. Они создают и удаляют собственные данные;
тест пула использует временную таблицу. Запускать Go-сервис для тестов не нужно.

Проверка линтером выполняется командой `make lint`.

## Реализованные ручки

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/v1/trips` | Создает поездку |
| `GET` | `/api/v1/trips/{tripId}` | Возвращает поездку по `tripId` |
| `POST` | `/api/v1/trips/{tripId}/finish` | Завершает активную поездку |
| `POST` | `/api/v1/trips/{tripId}/positions` | Сохраняет координату активной поездки и возвращает `201` |
| `GET` | `/api/v1/trips/{tripId}/positions` | Возвращает все точки маршрута по `recorded_at`, затем по `id`, по возрастанию |
| `GET` | `/health` | Liveness probe: возвращает `200`, пока процесс жив, без обращения к БД |
| `GET` | `/ready` | Readiness probe: проверяет PostgreSQL и возвращает `200`, если БД доступна, иначе `503` |

Ошибки API возвращаются в формате `application/problem+json`.

## Опрос устаревших поездок

PostgreSQL → Сканер → Приоритетная очередь → Воркеры → Push Service

Сохранение координаты → PostgreSQL
После commit → Отмена задачи в очереди

Сканер выполняет один запрос на каждом тике `POSITION_CHECK_INTERVAL`.
Обходы выполняются последовательно. SQL выбирает активные поездки, у которых
`COALESCE(last_position_at, started_at)` старше `POSITION_STALE_AFTER`, и
сортирует их по этому времени по возрастанию. Под выборку создан частичный
индекс `trips_active_last_position_idx` для статуса `active`.

Выборка возвращает все подходящие поездки за один запрос. После рестарта
сканер снова находит их в PostgreSQL на ближайшем тике.

### Очередь и отправка

Очередь реализована на `container/heap` и вмещает до `POSITION_QUEUE_SIZE`
ожидающих задач. Первыми извлекаются поездки с самым старым временем
последней активности. `POSITION_WORKERS` воркеров создаются при старте и
обрабатывают задачи последовательно в каждой горутине.

При заполненной очереди постановка сразу возвращает результат. Если новая
задача относится к более старой поездке, она вытесняет самую свежую ожидающую
задачу. В остальных случаях новая задача получает `dropped`. Дропы и
вытеснения увеличивают `tripgo.stale_checks{result="dropped"}` и
`tripgo.position_requests{result="dropped"}` и сопровождаются логом уровня `Warn`.

Поездка учитывается в структуре дедупликации от постановки до завершения
обработки. Повторная постановка в этот период получает `duplicate`.
Доступ к состоянию очереди защищён mutex. Идентификатор отдельной задачи
позволяет отличить повторную постановку той же поездки от старой задачи.

После успешного commit сохранения координаты ожидающая задача удаляется из
очереди, а для уже выполняющейся отправки отменяется контекст. Отмены во время
SQL-выборки также учитываются при последующей постановке её результата.

Каждая задача делает одну HTTP-попытку с таймаутом `PUSH_REQUEST_TIMEOUT`.
Гейтвей использует собственный `http.Client`, отправляет
`POST /api/v1/push` с `kind = "REQUEST_POSITION"`, `recipient_id = driver_id`
и `data.trip_id`. Успешный ответ Push Service имеет код `202`. Ошибки
транспорта и HTTP-коды возвращаются вызывающему коду, логируются и учитываются
в метриках, после чего воркер переходит к следующей задаче.

Условием повторного опроса служит возраст координаты в БД. При отсутствии
ответа устройства обработанная поездка снова может попасть в очередь на
следующем тике. Частота повторных проверок задаётся `POSITION_CHECK_INTERVAL`.

### Метрики и трейсы

| Метрика OpenTelemetry | Имя в Prometheus | Назначение |
|---|---|---|
| `tripgo.stale_checks{result}` | `tripgo_stale_checks_total` | Результаты постановки `queued`, `duplicate`, `dropped`, `canceled`, `closed` и дропы вытесненных задач |
| `tripgo.position_requests.queue.size` | `tripgo_position_requests_queue_size` | Число ожидающих задач |
| `tripgo.position_requests.workers.active` | `tripgo_position_requests_workers_active` | Число воркеров, выполняющих отправку |
| `tripgo.position_requests{result}` | `tripgo_position_requests_total` | Результаты `success`, `error`, `timeout`, `canceled` и дропы очереди |
| `tripgo.position_requests.duration` | `tripgo_position_requests_duration_seconds_bucket`, `_sum`, `_count` | Гистограмма длительности отправки в секундах |
| `tripgo.positions.saved` | `tripgo_positions_saved_total` | Число координат, сохранённых после commit |

Проверка сканера создаёт спан `positions.scan`. Обработка задачи создаёт
отдельный корневой спан `positions.process`, связанный со сканированием через
span link. Исходящий HTTP-запрос в Push Service инструментирован `otelhttp`.

Для наблюдения в Grafana используются панели `Queue size`, `Active workers`,
`Position request rate by result`, `Stale check rate by result`,
`Position request duration p95` и `Positions saved per second`.
Для счётчиков скорость вычисляется через `rate(...[2m])`, для p95 используется
`histogram_quantile` по бакетам гистограммы.

При нагрузочной проверке можно создать 200 активных устаревших поездок и
добавить задержку заглушке Push Service через `POST /admin/behaviour` с телом
`{"latency_ms":500}`. Очередь должна оставаться в пределах заданной ёмкости,
число активных воркеров ограничено `POSITION_WORKERS`, а переполнение видно
по `dropped`. После проверки задержка сбрасывается телом `{"latency_ms":0}`,
тестовые поездки завершаются. Скриншот метрик пула под нагрузкой прикладывается
к описанию PR.

## Принятые решения

### Работа с БД

Подключение к PostgreSQL сделано через `pgxpool`. На старте сервис выполняет `Ping`; если БД недоступна, сервис не запускается.

SQL строится через `squirrel` с placeholders `$1`, `$2`.

Пул инструментирован через `otelpgx`: запросы, в том числе внутри транзакций,
создают дочерние спаны текущего HTTP-трейса. Histogram
`db.client.operation.duration` записывает длительность в секундах и работает
независимо от trace sampling. Атрибуты запросов включают `db.operation.name`,
`db.collection.name` для таблиц `trips` и `trip_status_history`, а при ошибке —
`error.type` (SQLSTATE для ошибок PostgreSQL). SQL-текст и параметры не
записываются в атрибуты спанов. Integration-тест пула использует временную
таблицу в отдельной сессии и не меняет данные приложения.

### Корректное завершение работы

Сервис обрабатывает `SIGINT` и `SIGTERM`. На остановку выделяется общий
контекст с таймаутом `SHUTDOWN_TIMEOUT`.

1. HTTP-сервер прекращает принимать новые запросы и ждёт завершения текущих.
2. Сканер останавливается и закрывает очередь для новых задач.
3. Воркеры дорабатывают очередь в пределах оставшегося времени.
4. Закрываются простаивающие соединения HTTP-клиента Push Service, пул
   PostgreSQL и OpenTelemetry.

При исчерпании общего таймаута контексты HTTP-запросов и отправок в Push
Service отменяются. После завершения горутин освобождаются ресурсы.
Активные поездки с устаревшими координатами снова попадут в выборку после
рестарта сервиса.

### Менеджер транзакций

Менеджер транзакций реализует интерфейс:

```go
type TxManager interface {
    Do(ctx context.Context, fn func(ctx context.Context) error) error
}
```

`Do` открывает транзакцию, кладёт `pgx.Tx` в `context` и вызывает callback с
новым context. Если callback возвращает ошибку или паникует, выполняется
`ROLLBACK`. Если callback завершился успешно, выполняется `COMMIT`.

Repository не принимает транзакцию аргументом. Он достаёт executor из context:
если транзакция есть, запрос выполняется через неё; если нет — через
`pgxpool.Pool`.

Вложенный `Do` переиспользует уже существующую транзакцию.

### Уровень изоляции

Для транзакций выбран `ReadCommitted`.

Этого достаточно для лабораторной, потому что конкурентные инварианты защищены
на уровне SQL-операций и ограничений БД:

- запрет двух активных поездок на одного водителя обеспечивается partial unique
  index;
- при завершении `SELECT ... FOR UPDATE` блокирует строку поездки до конца
  транзакции. Конкурентный запрос ждёт снятия блокировки и проверяет актуальный
  статус поездки.

### Запрет двух активных поездок

В БД создан partial unique index:

```sql
CREATE UNIQUE INDEX one_active_trip_per_driver
ON trips (driver_id)
WHERE status = 'active';
```

PostgreSQL гарантирует это ограничение при конкурентных запросах. Ошибка PostgreSQL `23505` преобразуется в доменную ошибку `driver_busy`, которая на HTTP слое возвращается как `409`.

### Создание поездки

Бизнес-счётчики `tripgo.trips.created` и `tripgo.trips.completed` увеличиваются
только после успешного commit соответствующей операции. Ошибки репозитория,
занятый водитель, повторное завершение и ошибки commit не увеличивают их.
Счётчики не имеют лейблов с идентификаторами поездок или пользователей.

`CreateTrip` генерирует `id` на стороне сервиса, выставляет статус `active`, `started_at = now()` и `finished_at = NULL`.

В одной транзакции выполняются `INSERT` в `trips` и `INSERT` в
`trip_status_history`.

### Завершение поездки

`FinishTrip` внутри транзакции читает поездку по `id` через `SELECT ... FOR UPDATE`.
Если поездки нет, API возвращает `404 trip_not_found`. Затем `Trip.Finish`
проверяет, что поездка активна. При повторном завершении API возвращает
`409 trip_completed`.

Для активной поездки репозиторий обновляет статус, `finished_at` и `updated_at`
через `UPDATE ... WHERE id = $1` и записывает переход в `trip_status_history`
в той же транзакции.

### Координаты и маршрут

POST координаты принимает объект `coordinates` с `latitude` и `longitude`,
а также `recorded_at`. Широта должна находиться в диапазоне от −90 до 90,
долгота от −180 до 180. Время разбирается в формате RFC 3339 и может опережать
серверное максимум на минуту. Ошибки валидации возвращают `400 invalid_request`,
отсутствующая поездка возвращает `404 trip_not_found`, завершённая поездка
возвращает `409 trip_completed`.

Сохранение выполняется через `TxManager`. Строка поездки читается с
`SELECT ... FOR UPDATE`, затем точка вставляется в `trip_positions`,
а `trips.last_position_at` обновляется выражением
`GREATEST(last_position_at, recorded_at)`. Так запоздалая координата добавляется
в маршрут, а отметка последней позиции сохраняет более свежее значение.
Блокировка строки согласует сохранение координаты с завершением поездки.

GET маршрута возвращает все точки в массиве `positions`, отсортированные по
`recorded_at`, затем по `id`. Для поездки без точек возвращается пустой массив,
для отсутствующей поездки возвращается `404 trip_not_found`.
